## 背景

出展者情報・資料共有管理SaaSは、キャンプ・アウトドア展示会向けに、主催者が出展者から情報収集し、資料を公開・通知し、確認状況を管理し、個別請求書（銀行振込）の入金確認をするサービス。主催者が顧客（従量課金の通常プラン、または年間定額プラン）、出展者は無料利用。

設計ブリーフの【確定】事項は不変条件として維持し、【設計案】は本計画で実装可能な設計へ具体化し、【未確定】事項（価格・上限・締め日等）はすべて設定値として扱い、本番課金・本番公開前には反映しない。

## ブラッシュアップ提案（ブリーフに対する追加）

1. **公開URLへの不正・スパム登録対策** — 課金カウントが参加レコード数に直結するため、Bot/いたずら登録が主催者の実費コストに波及する。メール確認必須化に加え、レート制限・ハニーポット・CAPTCHA（イベント単位でトグル可能）を追加する。
2. **重複登録の具体的な検知ロジック** — `DuplicateFlag`（メール一致/社名類似）と主催者レビュー画面（O9）を追加する。
3. **インボイス制度（適格請求書）対応の要否** — `ServiceInvoice` への適格請求書発行事業者登録番号の記載要否を [open-decisions.md](./open-decisions.md) に追加。
4. **特定商取引法に基づく表記ページ** — カード課金を伴うオンラインサービスとして法的に必要な静的ページ（O19）を追加。
5. **同一企業・同一イベント内の複数ブランド出展の課金単位の明文化** — `EventParticipation` はブランド単位であり、複数ブランド出展は複数カウントになることを [data-model.md](./data-model.md) に明記。

これら以外はブリーフの設計方針をそのまま採用する。過去の拡張案（AIフォーム化、QR受付、コマ図自動配置等）は復活させない。

## 技術スタック

| 要素 | 採用 | 理由 |
|---|---|---|
| フレームワーク | Next.js（App Router）+ TypeScript | 主催者/出展者をルートグループで分離。Server Actionsでフォーム処理。 |
| ホスティング | Vercel | Cron機能で定期バッチ（課金確定・再通知）を賄う。 |
| DB/認証/ストレージ | Supabase（Postgres + Auth + Storage） | RLSを必須採用。非公開バケット＋署名URLでのみファイル配信。 |
| メール | Resend | 独自ドメインでSPF/DKIM/DMARC設定。トランザクションメール専用。 |
| 決済 | Stripe（推奨、最終比較は本番反映前に実施） | SetupIntent + off-session PaymentIntentで都度承認不要の自動課金。金額計算は自社台帳で行い、Stripeは決済実行レイヤーとしてのみ使う。 |
| ジョブ処理 | DBテーブル（`notification_jobs`）+ Vercel Cronポーリング | 初期コスト最小化。冪等性はアプリ側のユニーク制約で担保するため、将来Inngest等へ移行しても低コスト。 |
| 監視 | Sentry、UptimeRobot等 | 決済・通知失敗の検知、公開フォームURLの稼働監視。 |

## 実装フェーズ

各フェーズは「動かして確認できる単位」。前フェーズの受け入れ条件を満たしてから次に進む。

### Phase 0: リポジトリ基盤（本コミットで実施）
- Next.js/TypeScriptプロジェクト初期化、Supabase/Resend/Stripeクライアントのコード側準備（実credentials未接続）、SQLマイグレーション一式、RLSベースライン、`PricingConfig`/`AnnualPlanConfig`テスト値のseed、設計ドキュメント一式。
- **受け入れ条件**: `npm run build` / `npm run lint` が通る。`/health` ページが表示される。マイグレーションSQLが実Supabaseプロジェクトへ適用可能な状態である。

### Phase 1: 認証・組織・イベント管理の骨格
- 主催者サインアップ/ログイン、`organizer_organizations`/`organizer_memberships`、イベントCRUD（下書きのみ、公開フォームなし）。
- **受け入れ条件**: 主催者がサインアップ・ログインし、イベントを作成・編集できる。操作が`audit_logs`に記録される。

### Phase 2: フォーム設計・出展者情報収集（コア価値）
- フォームビルダー、公開URL発行、出展者の匿名下書き+メール確認+提出フロー、`event_participations`/`submission_versions`確定、`exhibitor_profiles`作成・再利用、重複検知フラグ、修正依頼→再提出、Excel/CSV出力（列選択・数式インジェクション対策）、スパム対策（レート制限・ハニーポット）。
- **受け入れ条件**: URLから事前登録なしで入力・メール確認・提出できる。主催者が一覧・Excel/CSVで取得できる。修正依頼→再提出で版が増える。重複登録候補が一覧表示される。

### Phase 3: ファイル公開・自動通知・確認状況
- `file_assets`アップロード（非公開ストレージ+署名URL）、`announcements`/`announcement_versions`/`announcement_audiences`、下書き→公開フロー、通知ジョブ、`notification_deliveries`冪等性キー、Resend連携、`acknowledgements`、未確認者への再通知、送信失敗の可視化。
- **受け入れ条件**: 下書き保存は非通知、公開時のみ通知。ジョブ再試行での二重通知なし（自動テスト）。失敗が主催者画面で把握できる。閲覧のみでは確認済みにならず版・日時付きで記録される。

### Phase 4: 請求書・入金管理
- `exhibitor_invoices`CRUD、Phase3通知基盤を再利用した公開通知、`invoice_ack_status`と`payment_status`の完全分離実装、`invoice_change_logs`、クロステナントアクセス不可の自動テスト。
- **受け入れ条件**: 個別支払期限を設定でき、請求書確認状態と入金状態が独立更新できる。主催者の手動変更で入金済みになり変更履歴が残る。他主催者・他出展者が請求書を取得できないことをテストで確認。

### Phase 5: SaaS従量課金（通常プラン）
- `service_contracts`(standard)、`usage_ledger`追記（idempotency_key付き）、ダッシュボードでの現在数・課金対象数・見込み請求額表示、Stripe SetupIntentでカード登録、`service_invoices`生成バッチ、off-session PaymentIntent自動課金、`payment_events`Webhook処理、決済失敗時の通知・再試行・カード変更導線、補正行機能。
- **受け入れ条件**: テスト設定値で30社=9,800円/31社=10,100円/87社=26,900円を自動テストで再現。追加枠購入UIなし。再提出・Webhook再送で二重計上されないことをテストで検証。未確定価格は本番未反映。

### Phase 6: 年間プラン
- `service_contracts`(annual)、`annual_plan_configs`、契約時/更新時カード決済、上限接近/超過時の主催者向け警告、通常⇔年間プラン変更の状態機械。
- **受け入れ条件**: 年間契約に従量請求が発生しないことを自動テストで保証。上限接近/超過時も出展者の入力・提出は継続可能。プラン変更の二重クリック/リトライで契約が二重化されない。

### Phase 7: 出力強化・権限強化・運用仕上げ
- 追加出力テンプレート、ZIP生成時のファイル単位再権限チェック、クロステナント否定テスト網羅、削除耐性テスト、スパム対策強化、特定商取引法表記ページ、バックアップ復旧リハーサル、監視・アラート整備。
- **受け入れ条件**: 出力ZIPに非公開メモ・他社請求書が混入しないことをテストで確認。決済失敗・重複登録訂正・資料更新後の再確認・出力時の権限違反の各シナリオが自動テストで再現・検証できる。

## 設計上のリスクと対策

- **課金カウントの単位ズレ**: 物理削除禁止・追記専用`usage_ledger`・同一トランザクション+ユニーク制約で構造的に防止。ダッシュボードは「現在有効数」と「累計課金対象数」を両方表示し差異を説明する。
- **Webhook冪等性**: 署名検証（Rawボディ）→`provider_event_id`ユニーク制約→前方遷移のみの状態機械→自社発API呼び出しにも`Idempotency-Key`付与、の4層で担保。
- **公開URLへのスパム登録**: メール確認必須化＋レート制限＋ハニーポット＋CAPTCHA（トグル）の多層防御。Bot起因の課金は理由必須の補正行で事後救済。
- **「事前アカウント作成不要」×「認可付きリンク」の両立**: 匿名下書き（draftトークン、メール不要）→提出確定境界でのみメール確認→以降は都度「メール入力→署名付き短期リンク」でパスワードレス再アクセス。通知メール内リンクは受信者+対象リソースID+有効期限を署名検証してから表示する。
- **プラン変更時の二重請求**: `service_contracts`のactive一意性をDB制約で保証、プラン切替を3ステップの単一トランザクションで実施。

## 検証方法

- 各Phase完了時：該当する受け入れ条件を自動テスト（特に課金・通知の冪等性、権限のクロステナントアクセス不可）として実装し、CIで実行する。
- Phase 5/6：Stripeテストモード、Resendテストドメインで実施し、実カード・実メール配信は行わない。
- UIが動く段階（Phase 2以降）では、実際にブラウザでフォーム入力→提出→主催者側一覧確認、という一連の流れを手動でも確認する。
