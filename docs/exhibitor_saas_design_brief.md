# 出展者情報・資料共有管理SaaS：Claude Code設計引き継ぎ

作成日：2026-09-08
状態：要件整理・設計開始用。サービス名未定。実装指示は末尾。

## 1. この資料の読み方

- 【確定】は会話でユーザーが明示または方向性を承認した内容。
- 【設計案】は実装に向けた提案。ユーザーが詳細まで確定した事実ではない。
- 【未確定】は設定可能にして設計を進め、価格公開・実課金等の前に決める事項。
- 途中の案より、最後のユーザー修正を優先する。不要な業務・機能を追加しない。

## 2. 目的・事業背景

キャンプ・アウトドア展示会では、出展者が複数のPDFへ似た情報を書き、メールで返送する手間がある。主催者にも、転記・集計・催促・資料送付・確認・入金管理の負担がある。

【確定】既存の情報収集をWeb入力に置き換え、主催者が管理・ダウンロードできるサービスを作る。ファイル公開時の自動メール通知と確認状況表示を加える。出展者は最初の情報収集時にURLを受け取り、入力から利用を開始する。

主な顧客はイベント主催者・運営会社。出展者は無料利用。最初はアウトドア・物販イベントを想定し、将来は合同展示会・定期マルシェなどへ展開可能な設計にする。

## 3. MVPの境界

### 含める

1. 主催者アカウント、イベント作成・管理。
2. Webによる出展者情報収集、イベントへの登録。
3. 提出情報の一覧・確認・修正依頼・出力。
4. 主催者によるファイル掲載、対象出展者への自動メール通知。
5. 資料ごとの出展者の確認状況表示。
6. 個別請求書の配布、個別支払期限、銀行振込の手動入金確認。
7. 出展者ページからの提出情報・資料・請求情報の確認。
8. 主催者に対するサービス利用料の自動計算・クレジットカード課金。
9. 大規模主催者向け年間定額契約。

### 初期には含めない

- 出展募集ポータル、応募審査・採否管理、集客、チケット販売。
- 出展料のカード決済代行、銀行口座との自動照合、請求書自動発行。
- コマ図の描画・自動配置、入退場QR受付、商談管理。
- 任意PDFのAIフォーム化、指定PDFの完全自動再現、AIチャット。
- LINE・SMS、ネイティブアプリ、自由なワークフローエンジン。
- 通常プランの利用枠の追加購入。年間契約への従量課金。

主催者の実際の業務は「出展募集→要項送付→情報収集→請求案内→コマ図案内→搬入搬出案内」。サービスは情報収集以降を中心に支援し、既存の募集・採択・振込方法を維持する。各業務は前後・並行するため、全出展者を一律の一本道の状態で管理しない。

## 4. 利用フロー

### 主催者

1. 主催者組織・イベントを作成。
2. テンプレートから入力フォームを設定し、情報収集URLを取得。
3. 既存のメール等で、出展が決まった相手へURLを案内。
4. 入力・提出した出展者を一覧で管理。
5. 必要情報をExcel・CSVなどでダウンロード。
6. 要項・コマ図・搬入搬出案内などのファイルをアップロードして公開。
7. 対象出展者へ自動メールが送信され、未確認・確認済みを一覧確認。
8. 個別請求書と支払期限を案内。銀行口座を確認し、入金済みに手動変更。

### 出展者

1. 情報入力用URLを開く。
2. ブランド・担当者等と必要な出展情報を入力し、メールアドレスを確認して提出。
3. そのイベントへ登録され、以後は自社ページで情報・資料・請求書を確認。
4. 通知メールから資料を開き、「確認しました」を押す。
5. 必要に応じて情報の修正・再提出を行う。

【確定】入力前に独立した面倒なアカウント作成フローを要求しない。
【設計案】本人確認はメール認証。通知からのアクセスは認証付きリンク等で本人と所属を確認する。URLを知っているだけで個別請求書が見える公開設計にはしない。

## 5. Webフォーム・情報管理

### 収集する代表項目

| 分類 | 内容例 |
| --- | --- |
| ブランド共通情報 | ブランド名、会社名、所在地、Web・SNS、担当者、連絡先 |
| 広報素材 | ロゴ、紹介文、商品写真 |
| 開催別情報 | 展示・販売内容、当日担当者、緊急連絡先 |
| 電源・備品 | 使用有無、機器名、消費電力、希望備品、数量 |
| 車両・搬入出 | 車種、ナンバー、台数、担当者、希望時間 |
| スタッフ | 氏名、参加日、パス希望枚数 |
| 添付 | 主催者が指定する書類・配置図など |

【設計案】基本の項目型は短文、長文、数値、日付、単一選択、複数選択、チェック、ファイル、繰り返し入力。必須・説明・並び順・締切と、電源ありの場合のみ詳細表示など単純な条件分岐を扱う。最初から高機能なフォームビルダーにしない。

【設計案】自動保存、途中再開、修正依頼、再提出、提出版の履歴を持つ。状態は「未提出／下書き／提出済み／修正依頼／確認済み」。主催者確認後の重要な変更は再確認対象とする。

【設計案】ブランドプロフィール・素材を保存して次回入力へ再利用できる。提出済みデータは提出時点のスナップショットを持ち、プロフィール変更で過去イベントを上書きしない。他主催者へ自動共有しない。

共通URLからの重複登録を検知し、主催者が無効化・整理できるようにする。ただしメール一致だけで会社を統合しない。同じメールが複数ブランドを担当する可能性がある。

## 6. ファイル公開・通知・確認

【確定】主催者が知らせたい資料を掲載すると、対象出展者にメール通知が届き、確認状況を管理できる。

【設計案】操作は「ファイル選択・アップロード→下書き→対象選択→公開して通知」。アップロード途中では送信しない。公開時の送信は自動で、別途メールを書く必要をなくす。

対象は全出展者、指定グループ、個別出展者。グループは屋内・屋外・飲食など簡単な分類。個別請求書は宛先企業だけに公開する。

資料にはタイトル、本文、添付、公開対象、公開日時、版、確認要求の有無を持たせる。ファイルはPDF・画像等。通知メールは要点と認証付き閲覧導線を中心にし、添付の大量配信を避ける。

### 状態の区別

- 送信状態：送信待ち／送信処理済み／失敗等。メール事業者の受付や配送と実際の確認を混同しない。
- 確認状態：未確認／確認済み。「確認しました」の明示操作を基準にする。
- 誰が・いつ・どの版を確認したか記録する。企業の担当者1名の確認でその出展者を確認済みにする案を初期値とする。

【設計案】主催者が未確認者だけへ再通知できる。自動催促は初期必須にせず追加可能にする。

【設計案】資料更新は新しい版として保存し、重要変更では再通知・再確認を要求できる。過去の確認記録は残す。後から登録した出展者は有効な全体資料を閲覧でき、初回通知にまとめる。キャンセル出展者への通常通知停止を可能にする。

通知はジョブ・送信記録を持ち、再試行しても同一版・同一受信者への意図しない二重送信を防ぐ。意図的な再通知は別操作として記録する。

## 7. 請求書・出展料の銀行振込管理

【確定】主催者が作成済み請求書を個別掲載し、出展者へ通知。出展者は銀行振込。主催者が手動で入金状態を変更する。

最低限の情報：請求書ファイル、対象出展者、金額、支払期限、請求書確認状態、入金状態、入金日、主催者内部メモ。

| 対象 | 状態 | 更新者 |
| --- | --- | --- |
| 請求書の内容確認 | 未確認／確認済み | 出展者 |
| 銀行振込 | 未入金／入金済み | 主催者 |

早割等に対応するため、支払期限と金額は出展者ごとに設定できる。期限経過で勝手に値上げ・請求書差し替えをしない。入金済み表示を出展者の自己申告で確定させない。

【設計案】訂正は可能とし、変更者・日時・変更内容を記録。一部入金・返金・追加請求の詳細処理は要件確認後に追加し、初期仕様を膨らませない。

## 8. 出力

主催者が必要情報をダウンロードできることが主要価値。Excel・CSV、元ファイルのダウンロード、素材ZIPを基本とする。

代表テンプレート：出展者一覧、電源・備品一覧、車両一覧、スタッフ一覧、ブランド紹介CSV＋ロゴZIP。

【設計案】必要な列を選択可能にする。権限と公開範囲を出力にも適用する。個別請求書や非公開メモを意図せず他社用ZIPへ入れない。フォーム入力値のCSV数式実行対策を行う。

共通レイアウトの提出控えPDFは設計候補。会場指定PDFへの転記・完全再現はMVP必須ではない。

## 9. SaaS利用料金：出展料とは別系統

ここでの支払者は主催者、受取者は本サービス。出展者が主催者へ払う銀行振込とは完全に区別する。

### 通常プラン

【現行料金案】税別、1開催9,800円、30出展者まで含む。31社目から1社300円。

料金式：9,800 + max(課金対象出展者数 - 30, 0) × 300。

例：30社9,800円、50社15,800円、87社26,900円、100社30,800円、300社90,800円。

【確定】枠の追加購入は行わない。出展者数から自動計算し、登録クレジットカードへ自動課金。主催者の都度承認操作は不要。画面には現在の出展者数を表示する。

【設計案】現在の利用料金、決済済額、未精算額も確認可能にする。カウントは初回提出完了のイベント参加レコード単位。同一参加レコードのスタッフ人数・コマ数で加算しない。同じ企業の別開催参加は別カウント。招待・下書きのみでは課金しない。

【設計案・未確定】基本料は利用開始時、超過分は月次、終了時に残額精算。これは会話で提案したタイミングであり、ユーザーが明示確定した締め日ではない。

【設計案・未確定】提出後キャンセルはカウントを維持。重複・テスト登録は訂正対象。訂正・返金・クレジット処理は実課金前に決める。現在の有効出展者数と累計課金対象数が異なるときは、両者の関係を説明できる表示にする。

### 年間プラン

【確定】大規模主催者向けに年契約を用意。年間固定料金のみ。従量課金・自動超過課金を付けない。「1開催300社まで」等の契約条件を設ける。

【現行条件案】1開催300社まで。年間開催上限を設定する。年6開催は会話上のたたき台であり未確定。

【未確定】年額、年間開催上限、300社上限のカウント定義、契約更新・中途解約・プラン変更、年度またぎイベントの扱い。

年間プラン価格を19万8,000円等と勝手に確定しない。通常プランと異なる契約ポリシーとしてモデル化し、設定値で変更可能にする。年間上限を超えて通常従量課金へ自動切替しない。

【設計案】契約時と年次更新時にカード決済。条件超過は事前に主催者へ案内し、上位契約・個別契約へ。出展者の入力が突然失われないよう、上限到達時の主催者向け制御と案内を設計する。

### 課金の実装条件（設計案）

- 金額計算はサーバー側、整数の円単位。消費税の処理・端数規則は別途確定。
- カード情報は決済事業者で保管し、アプリでカード番号を保存しない。
- 利用数・請求額・決済結果は別々に記録。集計再実行で重複請求しない。
- 決済Webhookの署名検証、再送・順序逆転への対応。
- カード決済失敗の通知・再試行・支払い方法変更。未払い時の猶予や制限は未確定。
- プラン変更による通常料金と年間料金の二重請求を防ぐ。
- 未確定料金はテスト設定で設計・実装を進め、本番課金は確定後。

## 12. 技術方針の候補

Claude Codeで開発。技術選定は未確定。過去に費用計算した候補はVercel、Supabase、Resend。カード課金はStripe等の決済事業者を比較して設計時に選ぶ。フレームワークはTypeScript系Web構成などを候補とする。

既存リポジトリがある場合は、その構成・AGENTS.md・既存認証を確認して合わせる。ライブラリや決済APIの仕様は実装時点の公式資料で確認し、この資料をAPI仕様書として扱わない。

必要要素：バックグラウンド送信、認証、ファイル非公開管理、メール送信ドメイン設定、監視、復旧手順、バックアップ。動画処理・常時AI推論は不要。

## 13. 受け入れ条件

1. 情報収集URLから、別の事前登録フローなしに出展者として利用開始できる。
2. 提出済み情報を主催者が一覧・Excel/CSVで取得できる。
3. ファイルの下書き保存では通知されず、公開時に指定宛先へ通知される。
4. 公開ジョブの再試行で意図せず二重通知しない。失敗を主催者が把握できる。
5. 資料閲覧のみでは確認済みにならず、明示確認が版・日時付きで残る。
6. 他主催者・他出展者がAPIやファイルURLから個別請求書を取得できない。
7. 個別の支払期限を設定でき、請求書確認状態と入金状態が独立している。
8. 主催者の手動変更で入金済みとなり、変更履歴が残る。
9. 通常料金は30社9,800円、31社10,100円、87社26,900円。追加枠購入操作がない。
10. 同一参加者の再提出や決済Webhook再送で利用数・請求が二重計上されない。
11. 年間契約には従量請求が発生しない。上限条件は設定可能で、未確定価格を本番適用しない。
12. 資料更新後の再確認、重複登録訂正、決済失敗、出力時の権限を検証できる。
